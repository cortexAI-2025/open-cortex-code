# Rapport de réalisation et de validation — 12 novembre 2026

## Portée et principe de preuve

Version de développement **0.1.0**, nom provisoire Open Cortex Coder. Les critères complets de l'application sont conservés dans `TODO.md`. La présente version est **une base locale utilisable et testable, pas une livraison complète de toutes les intégrations demandées**. Les fonctions ci-dessous ne sont dites opérationnelles que si leur comportement a été exercé. Un contrôle de configuration d'endpoint ne vaut pas test de génération, et la présence d'une vue ne prouve pas qu'un service distant fonctionne.

## Capacités effectivement exercées

- **OpenCode natif 2.2.7.** Le binaire local épinglé démarre son vrai serveur V2 avec authentification, `Location` et sessions; la version reçue est contrôlée. Les intégrations utilisent le client TypeScript officiel 2.2.7 plutôt qu'un moteur simulé.
- **Ask, Plan et Agent avec vraies générations locales.** Le harness a utilisé Ollama sur CPU avec `qwen3:1.7b`, sans clé distante et sans appel payant. Ask a inspecté une fixture et trouvé un bug sans modifier les fichiers; Plan a inspecté une fixture sans mutation; Agent a corrigé deux fichiers, a demandé les permissions de modification/commande et a lancé les tests réels `node --test`. La fixture était volontairement en échec au départ (2 échecs), puis les 2 tests ont réussi après corrections.
- **Sessions, mémoire de reprise et changement de modèle local.** Deux modèles Ollama locaux ont été chargés pour les scénarios; le connecteur a conservé la même session et les messages lors du passage entre eux. Ce résultat ne valide pas un changement vers un compte fournisseur commercial différent.
- **Connecteur local et sécurité de base.** Les tests ont exercé l'authentification de pairing, la vérification Host/Origin, le refus des origines hostiles, l'isolement des entrées de mémoire entre deux projets, la réponse sans clé, l'absence d'une clé témoin dans SQLite, la protection des chemins `.env`, les symlinks, les hardlinks, les écritures à hash obsolète et le refus d'exécuter un projet non approuvé.
- **Pairing UI HTTPS → loopback.** Les demandes distantes sont fermées par défaut; l'interface locale peut ouvrir une fenêtre de cinq minutes, après quoi une origine HTTPS précise doit encore être approuvée. Le bearer est lié à l'origine exacte, conservé en mémoire seulement et révocable. Les tests de contrat couvrent le cooldown, les plafonds 10/min et 32 entrées, CORS sans wildcard ni cookie, les preflights, le Host DNS-rebinding falsifié, les jetons incorrects ou d'une autre origine, le self-revoke et le refus des routes distantes de lecture/écriture des secrets BYOK/MCP/API. Un E2E navigateur réel a aussi été exécuté depuis l'origine HTTPS du site sur Chromium 156.0.8078.73 et Firefox 160.0 sous Ubuntu 24.04.5 ARM64 : permission réseau local affichée/acceptée, demande soumise, approbation locale, association UI puis déconnexion/révocation réussies. Profil temporaire, sans mémorisation de la permission, sans projet ni clé BYOK. Les résultats ne certifient pas d'autres versions/OS; les statuts HTTP détaillés ont été capturés pour Chromium, pas Firefox. Voir [`pairing-https-loopback.md`](pairing-https-loopback.md) et [`audit-architecture-locale.md`](audit-architecture-locale.md).
- **Édition et restauration de fichiers.** Les sauvegardes optimistes protègent un état précédent; la nouvelle route locale restitue les aperçus par projet et fichier, exige confirmation, revalide le hash courant et enregistre également l'état remplacé. Un scénario HTTP réel couvre le succès, l'absence de consentement, le conflit de hash et l'exclusion d'un chemin sensible.
- **Git réel.** Des fixtures temporaires exercent le statut, le diff, les commits, les branches, les checkpoints, la restauration avec hash prévisualisé et l'absence de modifications de l'index. Les critères des chemins d'accès aux secrets npm sont testés.
- **MCP local.** Un fixture local réel en JSON-RPC est lancé comme processus et répond à `initialize` et `tools/list`. Le test valide l'ajout désactivé, le refus de connexion en Ask, la connexion après activation Agent confirmée, l'état réel du moteur et la suppression. Il n'exécute pas une génération LLM ni un serveur MCP distant.
- **Mémoire, knowledge, Skills et commandes locales.** Le test d'intégration a créé deux projets et vérifié l'isolement des notes persistées, l'indexation/recherche de document, l'export local d'un Skill, le refus de commandes sur projet non approuvé, un `node --test` réellement exécuté, le diff Git, les checkpoints et le redémarrage avec reprise de mémoire.
- **Interface et compilation.** Le manifeste Preview `GET /manus-routes.json` a répondu HTTP 200 avec la route réelle `/`; la racine Vite a répondu HTTP 200. Le build inclut des workers Monaco locaux.
- **Desktop empaqueté Linux ARM64.** Le smoke test a réussi dans `release/linux-arm64-unpacked` et après extraction dans un répertoire temporaire du véritable `.deb` (sans installation système). Résultat Electron : `packaged=true`, santé du connecteur vraie, `engineVersion=2.2.7`, renderer 2 257 caractères visibles et `nodeExposed=false`, `bootstrap.advanced=true`, binaire natif `2.2.7`. Le coffre OS a indiqué `vaultAvailable=false` dans cet environnement de test; aucune persistance durable de secret n'y est donc annoncée. Ce test ne valide que Linux ARM64 et la génération locale de ces fichiers n'est pas une publication.

Les preuves expurgées des sessions moteur et les rapports détaillés des scénarios du connecteur/harness sont conservés dans l'environnement de travail, hors du dépôt public; ils ne sont pas nécessaires pour installer l'application.

## Capacités présentes mais partielles ou non validées en service réel

- **BYOK et fournisseurs.** L'interface et le connecteur prennent en charge des profils, des identifiants, endpoints personnalisés, une clé fournie par l'utilisateur, un coffre mémoire, la rotation/suppression et les credentials du modèle actif. Les tests prouvent l'absence de persistance d'une clé témoin en SQLite. Le test `/models` de l'application vérifie l'endpoint et son authentification lorsqu'une clé réelle est fournie — ce n'est explicitement pas une génération. **Aucune clé Z.ai, OpenAI, Anthropic, Gemini ou autre n'a été utilisée**; l'accès GLM-4.5 Flash/GLM-4.7 Flash, leurs quotas, coûts et l'appel d'outil chez un fournisseur distant ne sont donc pas validés. Aucune clé n'est intégrée ni aucun appel payant effectué.
- **Changement de modèle.** Continuité de session démontrée entre modèles Ollama; bascule inter-fournisseur distante encore à tester avec des credentials réels et autorisation de transmettre le contexte au nouveau fournisseur.
- **GitHub.** Les fonctions s'appuient sur le CLI `gh` local et annoncent les limites de connexion; cette livraison ne démontre ni OAuth GitHub, ni PR/merge/push, ni Actions/CI, ni webhooks/événements GitHub planifiés.
- **Agents parallèles.** Des worktrees, branches et états de tâches sont gérés localement; certains tests route utilisent un moteur simulé. Le harness n'a pas prouvé l'exécution simultanée de plusieurs générations autonomes sur des worktrees.
- **MCP et API externes.** Le handshake testé est limité à un serveur local fixture. Les MCP distants, OAuth, les outils de services tiers et les intégrations réelles GitHub, Supabase, Vercel, Stripe, Gmail, Notion, Drive et Calendar n'ont pas été authentifiés/exercés. Les profils REST/API sont configurables mais chaque cible externe exige validation réseau et credentials réels.
- **Automatisations.** Le scheduler local peut être utilisé quand le connecteur tourne; il ne constitue ni un service hébergé permanent ni une surveillance indépendante du cycle de vie de l'application. Les événements GitHub ne sont pas réalisés.
- **Preview et IDE.** L'ouverture de preview est limitée à une URL loopback autorisée, sans lancement automatique d'un serveur de projet, PTY permanent ou sandbox renderer pour le code visité. La Preview Manus HTTPS peut ne pas être autorisée par le navigateur à joindre loopback HTTP; le Web servi localement ou Desktop est le parcours prévu. Aucun test visuel général de l'IDE n'a été effectué; le test navigateur mentionné plus haut concernait uniquement le pairing.
- **Coffre Desktop.** La persistance durable est opt-in et doit être refusée si un coffre OS réellement sûr n'est pas présent. Les clés transmises au fournisseur quittent nécessairement l'appareil à destination de ce fournisseur.

## Limites techniques et fonctions non livrées

- Les permissions OpenCode, les worktrees Git et le runner borné ne sont **pas un sandbox OS**. Les outils ont les droits du compte local. Les projets non approuvés sont refusés pour l'exécution; pour du code non fiable il faut un environnement externe isolé configuré séparément.
- Aucun déploiement de production Manus, publication de la Preview Manus, transfert cloud de dépôts, télémétrie de code ou synchronisation des clés n'est réalisé. L'interface statique est publiée séparément sur GitHub Pages avec autorisation; cela n'héberge ni le connecteur local ni les projets/clés. La configuration de publication automatique Manus est confirmée désactivée. Le backend/base Manus provisionnés ne sont pas utilisés pour le code privé.
- Aucun build Android APK/AAB ni test de toolchain Android n'est livré. Les builds installables non Linux et la signature notarisation/certification Windows/macOS ne sont pas validés.
- Le paquet Debian est un artefact de test non signé; il utilise une URL de projet réservée sous `example.invalid` et l'icône par défaut Electron. Ces métadonnées doivent être remplacées avant toute diffusion publique; ce paquet n'est pas présenté comme une version de production.
- Pas de garantie de parité complète avec Codex, Claude Code ou Jules. La couverture reste ouverte sur toute clause non indiquée comme exercée ci-dessus; consulter les sections de statut de `TODO.md`.
- Les tests et le build émettent les avertissements Node SQLite expérimental, bundle frontend/Monaco important et directives `use client` ignorées dans cette SPA. Electron avertit aussi que `safeStorage.isEncryptionAvailable` est dépréciée. Le découpage fin du bundle, le remplacement par l'API asynchrone du coffre et le test navigateur visuel restent à améliorer.

## Décision de mise en service

Utiliser cette version en **développement local uniquement**, avec des projets de confiance, après lecture de [`securite.md`](securite.md) et [`utilisation.md`](utilisation.md). Les livrables fournis sont des builds Linux ARM64 non signés : `.deb` et ZIP portable. Le smoke test du `.deb` extrait a réussi; utiliser seulement sur une machine Linux ARM64 compatible, jamais comme installateur x86_64/macOS/Windows. Le coffre durable était indisponible dans le sandbox. Vérifier les clés et modèles localement, ne pas exposer le port de pairing, et approuver chaque mutation/commande. Une publication ou un déploiement ultérieur exige une autorisation distincte.
